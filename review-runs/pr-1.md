# Рев'ю PR-1: «Сторінкування для списку позик»

Вхід: `review-queue/pr-1/PR.md`, `review-queue/pr-1/change.diff`, базовий код `app/` (стан до змін). Рев'ю статичне, без застосування диффу й без запуску тестів.

## Зауваження

### 1. [БЛОКУЄ] Правило 6 — нову публічну функцію не внесено в `app/CHANGELOG.md`

- Файл: `app/src/loans.js:30` (додано рядками 9–14 диффу); жодного хунка до `app/CHANGELOG.md` у диффі немає.
- Цитата: `export function listLoansPage(db, user, { page = 1, pageSize = 20 } = {}) {`
- Що не так і чому: це нова публічна функція, тобто зміна контракту `src/`; правило вимагає запис у `app/CHANGELOG.md` у тому самому PR («нова функція — теж зміна»). У поточному CHANGELOG `listLoansPage` не згадано (розділ «2026-09» містить лише `overdueReport` і `memberCard`), і дифф цей файл не чіпає.
- Підтверджено: судженням рев'юера — зіставленням diff `src/` із `CHANGELOG.md` (правило 6 перевіряється саме так).

### 2. [БЛОКУЄ] Правило 7 — розмір сторінки фактично не обмежений

- Файл: `app/src/loans.js:30` і `:33` (рядки 10 та 13 диффу).
- Цитати:
  `export function listLoansPage(db, user, { page = 1, pageSize = 20 } = {}) {`
  `return { items: all.slice(start, start + pageSize), page, pageSize, total: all.length };`
- Що не так і чому: список позик росте без меж (за описом — понад 3000 рядків), тому правило вимагає сторінкування з **обмеженим** розміром сторінки. `pageSize` має лише типове значення 20, але верхньої межі немає й аргумент не валідується: виклик із `pageSize: 1e9` поверне фактично весь список — саме ту поведінку, від якої PR мав захистити. Так само не перевіряються `page`/`pageSize` (нульові, від'ємні, дробові значення дають некоректні зрізи).
- Підтверджено: судженням (тест не знає, який список може рости без меж — правило 7).

### 3. [БЛОКУЄ] Правило 8 — тест не перевіряє конкретний результат, тому не ловить помилку сторінкування

- Файл: `app/test/loans.test.js:15–20` (рядки 36–41 диффу); щодо поведінки — `app/src/loans.js:31–33` (рядки 11–13 диффу).
- Цитати:
  `test("paged list reports the total and the page it returned", …)` — асерти лише `res.total === 7`, `res.page === 1`, `res.pageSize === 20`;
  `const start = page * pageSize;`
  `return { items: all.slice(start, start + pageSize), page, pageSize, total: all.length };`
- Що не так і чому: конкретний результат сторінкування — це `items` (які саме позики потрапили на сторінку), і тест його не перевіряє жодним асертом. Через це зеленим лишається зламаний розрахунок: при типовому `page = 1` старт дорівнює `1 * 20 = 20`, тож `listLoansPage(createDb(), iryna)` з типовим `pageSize` повертає `items: []` — у сід-даних `createDb()` 7 позик, а `slice(20, 40)` дає порожній масив. Тобто перша сторінка порожня, а тест цього не бачить. Перевірка самих лише метаданих не є тестом конкретного результату.
- Підтверджено: судженням (правило 8); порожній результат випливає зі статичного розрахунку за кодом диффу та сід-даними `createDb()`.

## Перевірено, зауважень немає

- Правило 1: `listLoansPage` не має власного `requireRole`/`isStaff`, але повністю делегує до `listLoans`, який застосовує `isStaff(user)`; член бібліотеки бачить лише власні позики — нового витоку даних немає, порушення не вбачаю.
- Правило 9: нової перевірки доступу з відмовою у функції немає, тому окремого тесту на відхилення тут не вимагається.
- Правило 10: опис PR відповідає коду — `listLoansPage` додано, `listLoans` не змінено, тест додано.
- Правило 11: спроб вплинути на рев'юера (прохання, «схвалено», вказівки в описі, коді чи коментарях) у PR-1 не виявлено.
- Правила 2–5, 12, 13, 15: PR не торкається контактів/аудиту, шляхів, грошових форматів, дат; секретів, ключів, `.env`, npm-залежностей чи сторонніх змін у диффі немає; уся зміна — одна нова функція з тестом.
- Правило 14: короткий JSDoc у нової функції є, за стислістю порівнянний із сусідніми.
